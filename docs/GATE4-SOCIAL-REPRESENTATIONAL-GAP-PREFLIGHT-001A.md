## Bounded Deep Audit Before Any Future Implementation

### Layer classification

This card is located at the mechanism hypothesis layer, but `001A` itself is
only a drafting task. A future `001B` may test whether a scripted social process
contains a representational gap. It must not test real-world relationship
learning, user modeling, agent personality, or product behavior.

### Strongest baseline explanation

The strongest baseline explanation is that any apparent `social_latent_state`
effect is solved by cheaper controls:

```text

bounded-order window model

```

If these controls match or beat the candidate under a frozen fair-access
contract, the correct verdict is baseline equivalence or collapse, not a
partial pass.

### Strongest reason this task may be invalid

The task may be invalid if the future scripted social process is merely an
ID-conditioned lookup problem or a transcript-summary retrieval problem. It may
also be invalid if the hidden partner state leaks through labels, fixture names,
partner keys, split IDs, filenames, artifact paths, or future partner responses.

### Falsification condition

The current framing is falsified if any required challenger family solves the
future distribution under the same allowed access, or if the distribution cannot
hide partner-state transitions without leaking labels or collapsing into a
bounded-order window, count/statistic, graph/cache, profile-table, retrieval, or
imitation solution.

This `001A` task does not test a mechanism. A future `001B` would still be only
a social representational-gap preflight, not a Gate4 mechanism pass. The target
is to test whether a future distribution resists cheap representational
controls. It is not to produce behavioral resemblance.

## Problem Definition

Draft a falsifiable social representational-gap preflight card for a future
Gate4 synthetic setting. The future preflight should test whether a scripted
social process requires latent-state inference across interaction history and
cannot be represented by cheap controls such as partner-ID lookup, static
per-partner profile tables, count/statistic tables, bounded-order window
models, graph/cache families, transcript retrieval, or summary retrieval.

The wrong problem is:

```text
build a social agent
simulate a relationship
create a user model
make behavior look alive
make Gate4 pass
enter same-agent bridge
connect this to EGO
```

The correct problem is:

```text
Can a future synthetic partner process be specified so that fair cheap controls
cannot solve it, while leakage and lookup triviality are actively ruled out?
```
