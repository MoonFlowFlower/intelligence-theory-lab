# EGO-MAINLINE-POST-ADMISSION-ROUTING-001A

## Mode

Post-admission routing / boundary classification / non-authorization audit only.

## Layer

Evidence-governance / bounded post-admission routing only.

This task does not enter runtime, implement EGO, authorize bridge runtime,
authorize Gate4 execution, choose a winning theory, or claim mechanism,
theory, architecture, agency, selfhood, consciousness, emotion, relationship
learning, stable user benefit, or future runtime correctness.

## Problem Definition

Given that `EGO-MAINLINE-ADMISSION-EXECUTION-001A` passed only at the bounded
evidence-governance layer, compute the next-stage routing boundary. The output
must classify what the project is allowed to do next, what remains blocked,
which upstream evidence boundaries are required, and what the next bounded task
class should be.

## Current Stage

Post-admission governance routing after sealed bounded admission execution.

## Hypothesis

A passed bounded admission execution should route to a next governance/planning
boundary, not to runtime implementation. A correct routing classifier preserves
the claim ceiling, carries forward non-authorization constraints, and produces
an executable next-task recommendation with explicit blocked alternatives.

## Strongest Baseline Explanation

The strongest baseline is verdict-only advancement: if the prior verdict says
pass, a naive router may over-route toward downstream execution. That baseline
is unsafe because it ignores claim ceiling, non-proven items, remote-anchor
verification, artifact inventory, and forbidden authorization boundaries.

## Strongest Reason This Task May Be Invalid

This task can only classify post-admission governance routing. It can produce a
well-formed boundary while adding no new mechanism evidence, no bridge-runtime
evidence, no Gate4 evidence, and no EGO runtime evidence.

## Falsification Condition

The current framing is falsified if the required commit or remote tag cannot be
verified exactly, prior admission artifacts are missing, claim ceiling or
non-proven constraints are absent, ablations skip real reruns, leakage positive
control is not detected, replay merely compares stored hashes or verdict
strings, or any route computation authorizes runtime, bridge runtime, Gate4
execution, implementation, or readiness claims.

## Insufficient Evidence

Even a passing routing audit is insufficient evidence for EGO readiness, bridge
readiness, runtime readiness, Gate4 readiness, mechanism validity, theory
validity, architecture correctness, agency, selfhood, consciousness, emotion,
relationship learning, stable user benefit, future runtime correctness, or
runtime authorization.

## Mechanism Test Classification

This task is not testing mechanism and is not producing behavioral resemblance.
It tests evidence-governance routing and non-authorization preservation only.

## Baselines

1. `naive_pass_to_advance_baseline`
   - Input: prior verdict only.
   - Expected behavior: over-routes from pass to advance.
   - Purpose: demonstrate why verdict-only routing is unsafe.

2. `claim_ceiling_baseline`
   - Input: prior claim ceiling and non-proven list only.
   - Expected behavior: blocks runtime, bridge runtime, Gate4 execution, and
     implementation unless separate readiness evidence exists.
   - Purpose: independent safety baseline against candidate routing.

- repository cleanliness/read-only mutation constraints;

The router must output:

- `allowed_next_routes`;
- `blocked_routes`;
- `required_missing_evidence`;
- `downstream_non_authorization_flags`;

- stop conditions;
- rollback plan.

The result may recommend only a bounded next task and must not authorize runtime
or Gate4 execution merely because 001A passed.

## Ablation Requirements

Rerun candidate routing under real interventions:

- remove prior verdict;
- remove claim ceiling;
- remove remote tag verification;
- remove non-proven list;
- remove repository inventory;
- remove forbidden authorization list;
- substitute a failing prior verdict;
- substitute an unverified remote tag;
- substitute a positive-control artifact containing unauthorized readiness
  claims.

Each ablation must recompute routing. If runtime, bridge runtime, Gate4
execution, consciousness, selfhood, relationship learning, or implementation is
authorized under missing or corrupted governance inputs, the task fails.

## Contrast Requirements

Compare candidate routing against both baselines:

- candidate must be stricter than `naive_pass_to_advance_baseline`;
- candidate must not exceed `claim_ceiling_baseline` unless independently
  computed upstream evidence justifies it;
- any stricter or looser decision must include computed reason codes.

## Leakage Scan Requirements

Implement a scanner with at least one positive-control case. Scan generated
markdown, JSON, and text artifacts for positive unauthorized claims while
distinguishing restraint, negation, blocked-route, and scanner-test language
where feasible.

Positive-control leakage must be detected. Generated artifacts must not contain
positive authorizations outside allowed restraint or test-control context.

## Replay Requirement

Create serialized `routing_state.json` containing input observations, prior
anchor readback, artifact inventory digest, candidate routing inputs, routing
parameters, run id, and seed/context identifiers if used.

Replay must recompute the candidate route from serialized state plus
observation. It must not merely replay hashes or stored verdict strings. Replay
output must match the originally reported routing decision and reason codes.

## Computed-Evidence Provenance Gate

leakage result, and replay metric must be derived from callable computation
paths. Every score or verdict-like value must record producer function, input
artifacts, run id, seed/context/episode identifiers if applicable, aggregation
rule, code path hash, and output artifact path.
